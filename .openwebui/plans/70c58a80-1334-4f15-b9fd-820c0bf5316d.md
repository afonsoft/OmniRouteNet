## 1. User Story

**As a** mantenedor do LLMRouter,
**I want** concluir a migração em relação ao OmniRoute (`cheaper-inference/OmniRoute`, branch `release/v3.8.53`, tip `785a357631c10591c158cf02700d6ec84c11be57`),
**So that** o port C#/.NET seja par, auditável e rastreável ao upstream — sem funcionalidade anunciada ausente e sem drift silencioso de versão.

**Problem context.** A migração do núcleo está madura: gateway nos 4 formatos (`/v1/chat/completions`, `/v1/messages`, `/v1/responses`, `/v1beta/*`), 20 estratégias de combo, resilience (breaker, cooldowns, quota windows, typed availability), registry com 3.262 providers, ~818 endpoints ASP.NET, 100 páginas Blazor, i18n en/pt-BR/es 100%. Porém: (a) 9 SPECs aprovadas (154–162) não têm código; (b) o pin upstream registrado (`412319f0`, 2026-10-26) está **5.812 arquivos** atrás do tip atual de `release/v3.8.53`; (c) o upstream adicionou Teams multi-tenant (18 arquivos), MFA/SSO (26), sing-box (15), 29 fluxos OAuth de CLI-agents, 18 serviços novos em `src/sse/services/` e 31 rotas de API novas.

## 4. Requirements

**RF-001 — Device authorization para CLI (SPEC-154)**
- Description: fluxo device-code para o CLI aprovar tokens via dashboard.
- Rules: `POST /api/cli/device` gera `{deviceCode,userCode,verifyUrl,expiresIn,interval}`; `POST /api/cli/device/token` faz polling → `pending|approved{token,scope:cli}`; página `/cli/device?code=` aprova/nega para usuário logado; persistência em `cliDeviceCodes`; deny, expiry e wrong-code são estados terminais.
- Input → Output: `{}` → device payload; `{deviceCode}` → status/token; UI → aprovação gravada.

**RF-002 — Test-mode API para e2e (SPEC-155)**
- Description: endpoints de fixture gated por env.
- Rules: `LLMROUTER_TEST_MODE=1` habilita; fora dele → 404. `POST /api/test/reset` (recria DB), `/api/test/seed` (fixture mínima idempotente: provider fake, key, combo), `/api/test/clock {offsetSec}` (clock skew p/ quota window), `/api/test/fail {provider,code,pct}`. `e2e/smoke.mjs` passa a usar seed.

**RF-003 — Audit/log HTTP sinks (SPEC-156)**
- Description: reenvio de eventos de audit/log para HTTP externo.
- Rules: `settings.sinks=[{id,name,type:audit|logs,url,headers{}}]`; BackgroundService + bounded channel; NDJSON batch (5 s / 50 itens); retry 3× com backoff; drop-oldest quando cheio; `POST /api/sinks/:id/test` valida conectividade; sem bloqueio do hot-path do gateway.

**RF-004 — SBOM + provenance no release (SPEC-157)**
- Description: artefatos de supply-chain no pipeline de release.
- Rules: `release.yml` gera SBOM (Syft) por artefato + provenance (attest-build-provenance) e anexa ao GitHub Release; sem alterar `ci.yml`.

**RF-005 — Upstream release contract + rebaseline (SPEC-158)**
- Description: manifest versionado do upstream comparado.
- Rules: `docs/release-manifest.json` com repo/tag/commit/data/escopo; validador determinístico (tag→commit, schema, duplicatas) roda em CI; contagens evidência (providers, rotas, páginas); revalidação classifica `ported|partial|intentionally out of scope|missing`. **Rebaseline imediato para commit `785a357631c10591c158cf02700d6ec84c11be57`** com diff-scan (5.812 arquivos vs pin antigo) publicado em `docs/analysis/omniroute-gap-785a3576.md`.

**RF-006 — Provider operations parity (SPEC-159)**
- Description: operação de providers no nível do upstream.
- Rules: agrupar por auth/categoria com contadores; filtro configured-only; batch test com concorrência limitada (nunca bloqueia pipeline, nunca expõe credenciais); exibir health, last-test, cooldown, quota-window, credential-expiration; manter CRUD/API compatível.

**RF-007 — Routing decision observability (SPEC-160)**
- Description: cada request roteado é explicável.
- Rules: attempt ledger persistido por request: ordem de candidatos, estratégia, skips + motivo, status, latência, cooldown, resultado de predicates, alvo selecionado; endpoint estável `GET /api/logs/{id}/route-decision`; exibição na tela Logs; cabeçalho de decisão nas responses do gateway (paridade com metadata upstream).

**RF-008 — Dashboard fidelity fixtures (SPEC-161)**
- Description: manifest de paridade UI auditável.
- Rules: `tests/fixtures/ui-parity.json` mapeia cada rota `src/app/(dashboard)/dashboard/**` do upstream ↔ página .razor ↔ status; teste falha se rota upstream core sem mapeamento ou status inválido; cobertura de i18n keys e temas é verificada.

**RF-009 — Compatibility/upgrade validation (SPEC-162)**
- Description: upgrades de dados não quebram.
- Rules: fixture SQLite do OmniRoute v3.8.53 + teste de import round-trip (providerConnections, apiKeys, combos, usageHistory); teste de upgrade de schema do LLMRouter (migrações EF aplicáveis de N-1 → N).

**RF-010 — OAuth CLI-agents (29 providers)**
- Description: paridade de OAuth do upstream (`src/lib/oauth/providers/`: antigravity, devin-desktop, muse-code, kimi-coding, trae, qoder, kilocode, freebuff, codebuddy-cn/intl, grok-cli/-oauth, zed, zed-hosted, cline, kiro, codex, cursor, claude, github, ghe-copilot, gitlab-duo, agy, openference, workbuddy, xai-oauth…).
- Rules: fluxos device/PKCE parametrizados pelo bloco `oauth` do registry; `clientIdEnv`/`clientSecretEnv` obrigatórios (sem segredo embutido — push protection); refresh token; documentar env vars por provider em `docs/oauth-import.md`.

**RF-011 — Port dos 18 serviços novos de `src/sse/services/`**
- Description: semântica de gateway 1:1.
- Rules: portar authTerminalStatus, comboTimeoutSessionAffinity, connectionModelInventory, expiryFirstAccountSelection/Metrics, githubCreditLimitPolicy, githubResponsesFallback, modelScopedQuotaFailure, museSessionOwnership, quotaLimitPolicy, quotaPreflightPolicy, requestShape, sameAccountTransportRetry, sessionAffinityPin, tokenRefresh, noAuthProviderSettings, model, auth para `src/LLMRouter.Core/Gateway|Resilience|Routing`; cada serviço com teste unitário que espelha o comportamento do upstream.

**RF-012 — Teams multi-tenant** *(condicionado à Open Question #1)*
- Description: custos e membros por time.
- Rules: entidades `teams`, `teamMembers`; rotas `/api/teams`, `/api/teams/[id]`, `/api/teams/[id]/members`, `/api/teams/[id]/usage`; página `Costs/Teams` com usage por time; permissão por time nas chaves.

**RF-013 — MFA TOTP** *(condicionado à Open Question #1)*
- Description: MFA na conta de admin/usuários.
- Rules: `/api/auth/mfa/{setup,enable,verify,disable,status}`; TOTP (RFC 6238) na entidade User; UI em Profile; re-auth para settings sensíveis (paridade com v3.8.53).

**RF-014 — Rotas API novas restantes**
- Description: 31 rotas novas do upstream, menos as cobertas por RF-001..013.
- Rules: `combos export/import`, `monitoring/model-health`, `oauth/[provider]/import-export`, `pricing/unpriced-usage`, `usage/availability`, `v0/management/{api-call,auth-files,reset-quota}`, `quota-recoveries/[id]`, `systemone`, `settings/cli-versions`, `cli-tools/whycodes-settings` — cada uma mapeada para endpoint ASP.NET com contrato igual ao upstream (request/response shapes).

**RF-015 — Páginas de dashboard faltantes**
- Description: ~15 páginas novas + sub-rotas de settings.
- Rules: portar layout/i18n fiéis (Tailwind classes verbatim, Material Symbols, CSS custom properties do `app.css`); páginas: acp-agents, agent-skills, audit/a2a, audit/mcp, cache/media, chaos, cli-code/[id], cloud-agents, discovery, free-provider-rankings, free-tiers, leaderboard, memory, omni-skills, orchestration, plugins/[name]/config, providers/new, providers/services, radar/{combos,intel,offers,setup}, resilience/{connections,cooldowns}, search-tools, settings/* (14 sub-rotas), system/{1proxy,mitm-proxy,proxy}, tools/agent-bridge, webhooks; reusar `PlaceholderPage.razor` só onde upstream é stub.

**RF-016 — Reconciliação de specs/docs (SPEC-145)**
- Description: rastreabilidade das 164 SPECs.
- Rules: SPECs executadas marcadas; README de `.specs/` com índice de status; pendências atualizadas.

**Business rules / invariants**
1. Nenhum segredo/credential em código ou JSON de registry — sempre env vars (push protection).
2. Hot-path do gateway nunca bloqueia por sink/telemetry (bounded channels, fire-and-forget com drop).
3. Contratos de API existentes permanecem compatíveis (backward compat verificada por testes de round-trip).
4. Port fiel: semântica upstream 1:1 salvo classificação explícita `intentionally out of scope` no manifest.
5. Test-mode endpoints nunca existem em produção sem `LLMROUTER_TEST_MODE=1`.

## 5. API Contract (resumo das novas)

| Método | Rota | Auth | Erros |
|---|---|---|---|
| POST | `/api/cli/device` | admin session | 401, 429 |
| POST | `/api/cli/device/token` | público (deviceCode) | 400 wrong-code, 410 expired |
| POST | `/api/test/{reset,seed,clock,fail}` | gated TEST_MODE | 404 fora do modo |
| POST | `/api/sinks/:id/test` | admin | 400 sink inválido, 502 upstream |
| GET | `/api/logs/{id}/route-decision` | api-key/admin | 404 sem ledger |
| GET/POST/PATCH/DELETE | `/api/teams[...]` | admin | 400/404/409 |
| POST | `/api/auth/mfa/{setup,enable,verify,disable}` | session | 400 código inválido |
| GET | `/api/monitoring/model-health`, `/api/usage/availability`, `/api/pricing/unpriced-usage` | admin | — |
| GET/POST | `/api/combos/export`, `/api/combos/import` | admin | 422 payload inválido |
| POST | `/api/v0/management/{api-call,auth-files,reset-quota}` | api-key admin | 403 |

Contratos detalhados por rota serão derivados 1:1 dos `route.ts` do upstream (fonte: `/tmp/omniroute` @ `785a3576`) durante a execução de cada sub-SPEC.

## 6. Acceptance Criteria

**BDD (cenários principais):**
- AC-01: **Given** ambiente sem `LLMROUTER_TEST_MODE`, **When** `POST /api/test/seed`, **Then** 404.
- AC-02: **Given** device code emitido, **When** aprovado na página `/cli/device?code=`, **Then** polling `/api/cli/device/token` retorna `{token,scope:cli}`.
- AC-03: **Given** sink configurado caído, **When** 60 eventos de audit, **Then** nenhum evento bloqueia request do gateway; channel faz drop-oldest; retries 3× com backoff.
- AC-04: **Given** combo com fallback e 1º candidato em cooldown, **When** request via gateway, **Then** `GET /api/logs/{id}/route-decision` mostra candidato 1 skip (cooldown) + candidato 2 selecionado, com latência e estratégia.
- AC-05: **Given** manifest com commit ≠ tag resolvida, **When** validador roda, **Then** CI falha com diff explícito.
- AC-06: **Given** DB do OmniRoute v3.8.53 exportado, **When** import no LLMRouter, **Then** providers/keys/combos/usage íntegros (round-trip idempotente).
- AC-07: **Given** provider OAuth kimi-coding com env vars setadas, **When** connect, **Then** device-flow completa e token persistido com refresh.
- AC-08: **Given** página upstream `dashboard/resilience/cooldowns` sem mapeamento no fixture, **When** teste de paridade roda, **Then** falha apontando a rota faltante.
- AC-09: **Given** release `v*` tag, **When** workflow de release roda, **Then** Release contém binários + SBOM + provenance.
- AC-10: **Given** team com 2 membros e keys atribuídas, **When** `GET /api/teams/{id}/usage`, **Then** usage agregada por membro filtrada pelo time. *(condicionado a OQ#1)*

**Edge cases:**

| Scenario | Input | Expected behavior |
|---|---|---|
| Device code expirado | poll após `expiresIn` | `410 gone` / estado `expired` |
| Sink URL inválida | `/api/sinks/:id/test` | 502 com mensagem sanitizada (sem stack) |
| Seed idempotente | 2× `POST /api/test/seed` | segunda chamada não duplica fixtures |
| Ledger sem fallback | request com único candidato ok | ledger com 1 entrada, sem skips |
| Import com combo órfão | provider removido no export | import marca combo com referência stale (sem crash) |
| MFA re-auth | alterar settings sensíveis sem verificação recente | 403 até re-verificar TOTP |
| OAuth sem env var | provider OAuth sem `clientIdEnv` | erro claro listando a var faltante |
| Batch test de 500 conexões | Providers page | concorrência limitada (bounded), UI não trava |
